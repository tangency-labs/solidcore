Updates: WR-161

#### WR-161 (update, 2026-10-31). `Duvv` and `Dvvv` can add `Buvv` / `Bvvv` under the opt-in `offset_surface_third_derivative_terms`
- **Location:** `source/SMLib/src/SmOffsetSurface.cpp:1482` and `:1491`, `SmOffsetSurface::EvaluatePlainOrSimple` (pinned v1.0.1); `crates/solidcore/src/surface/offset_surface.rs`.
- **What changed:** `Kernel::fixes.offset_surface_third_derivative_terms` (`UpstreamFixes`, **off by default**, pinned C++ parity) corrects exactly four third-order terms. This record's two:
  1. `Duvv` is written as `Buvv + d * Nuvv` (`d(1, 2)`), not `Buuv + d * Nuvv` (`d(2, 1)`).
  2. `Dvvv` is written as `Bvvv + d * Nvvv` (`d(0, 3)`), not `Buuv + d * Nvvv` (`d(2, 1)`).
  The other two, from `WR-160`, correct the `Cuuv` coefficient (`1.0`, not `3.0`) and the `Cuvv` coefficient (`-1.0`, not `3.0`). Orders 0..2 and `Duuu` are unchanged; with the flag off the output is bit-identical to before.
- **Evidence:** the new focused `surface::offset_surface::tests` build the biquadratic Bezier base `B(u, v) = (u + u^2 v, v + u v^2, u v)` through the public `BSplineSurface::from_data`, construct a public `OffsetSurface::new` and evaluate through the public `OffsetSurface::evaluate(uv, 3, 3, flags)` with `flags.only_upper_half = true` at two asymmetric UV points and `d = +0.125` / `-0.125`. The upper triangle contains derivatives with total order at most 3; this is not a full rectangular `(3, 3)` request, which exceeds the existing bound. The closed-form oracle is `B + d q / sqrt(L)`, `L = 1 + u^2 + v^2 + 6uv + 9u^2v^2`, checked to `1e-10` relative without an absolute floor. `Buvv = (0, 2, 0)` and `Bvvv = (0, 0, 0)` both differ from `Buuv = (2, 0, 0)`, so both wrong bases are caught: at `d = 0.125`, `uv = (0.25, 0.5)` the corrected `Suvv = (-0.073477204663, 1.884574138045, 0.009817341315)` and `Svvv = (-0.161697725660, 0.012630381645, 0.070751767665)`. The default path visibly disagrees with both. The tightened relative assertion is rechecked by the parent after the writer handoff.
- **Still unfixed:** `WR-162` (upper-half, unequal-order second-derivative slot write) is separate and remains. No claim is made about `SM_API` higher derivatives or an end-to-end `CrvOnSurf` improvement; an in-kernel `CrvOnSurf` evaluator that reads the third partials can consume the corrected values, but no production case that does was measured.
- **Confirmed:** the Rust default/opt-in values are measured by the new tests; this biquadratic counterexample has not been newly replayed in C++. Reading the pinned C++ confirms `Buuv` in both source terms. Default native fixtures are unchanged; no flag-on C++ agreement is claimed.

#### WR-614. The crossing line of two planes within tolerance of each other across a narrow strip fails the merge
- **Severity:** Wrong result (a boolean of valid bodies fails with `SM_ERR`)
- **Area:** Booleans
- **Location:** `source/SMLib/src/SmTopologyIntersector.cpp`, `SmTopologyIntersector::IntersectInsertRelate` (def. `:1092`), which resolves (`ResolveIntersections`, def. `:2251`) every face/face proto edge it found; `source/SMLib/src/SmProtoTopology.cpp`, `SmProtoVertex::GetFinalVertex` (def. `:2143`); the failure is reported by `SmMerge::MakeFaceuse` (`source/SMLib/src/SmMerge.cpp`, `SER(SM_ERR)` when the Brep mate of an edge use's vertex is neither end of the Brep edge, `:7077`).
- **What happens:** Two planar faces crossing at a small angle meet in a line fixed only to `tol / sin(angle)`. When an edge of each face lies on the other face within tolerance, parallel to the crossing and on either side of it, the faces are within tolerance of each other across the whole strip between those edges, yet the crossing still becomes an edge definition. Its end proto vertices (capture distance 0.01) hold two correctly classified vertex definitions, one on either side of the crossing: an end vertex of each bounding edge. `GetFinalVertex` picks, per body, the one nearest and connected to that body's source face, so the two bodies' edges end at different vertex definitions, and `SetRelationships` relates vertices only within one definition. `MakeFaceuse` then finds the edge's vertex mates inconsistent and fails. Picking one definition for both bodies would leave the curve farther from its vertex than the tolerance. ProtoFaces only detect coincident surfaces, never non-parallel planes coincident along a strip.
- **Trigger:** two 4 mm cubes, B turned 5.7 deg about z, whose faces (A's y = 20, B's F1) cross at x = 1.99995 and stay within 5e-6 of each other across x in [1.9999, 2]: B's corner edge lies on A's face, A's corner edge on F1, overlapping by about 1.0e-4 mm (the issue's imported bodies, intersection tolerance 5e-6). Both bodies pass the B-rep check; Intersect returns `SM_ERR` (1001). Rebuilt from primitives at the default tolerances, the same cubes within 1e-5 across x in [1.9998, 2] fail the union with `SM_ERR` from `MakeFaceuse`.
- **How found:** reported in tangency-labs/solidcore#1794 (SolidCraft, from the fork's batch-4 bodies). No fix in the fork (tangency-labs/smlib main and the batch branches) or upstream.
- **Confirmed:** yes, on the C++ build: `boolean.api_brep` fixture `fixtures/boolean.api_brep/wr614_coincident_strip.json`, case `wr614_strip_union_d1e-05` (`SmApiBooleanUnion` of the cubes rebuilt from primitives, within 1e-5 across x in [1.9998, 2], default tolerances), fails with the same status on both sides; the Rust test `crates/solidcore/tests/wr_614_coincident_strip_crossing.rs` (`wr_614_union_fails_upstream`) fails the same union with `SM_ERR` from `MakeFaceuse`. The other 23 cases of the fixture agree as well.
- **Workaround:** the same union through `SmApiBooleanWithOptions` with the post-process flag (`bBooleanPostProcess`) succeeds on both sides (case `wr614_strip_measured_union_d1e-05`).
- **Rust port:** behaves as upstream by default. With the opt-in `Kernel::fixes.boolean_coincident_strip_drops_crossing` (own design), `intersect_insert_relate` removes, before resolving, the face/face edge definition of two planes (and its proto edge when that is left without one) when an edge-on-face edge definition of an edge of one face on the other runs parallel to it, covers it and lies farther from it than the tolerance, either in the same proto edge (the cubes above: B's corner edge on A's face is combined into the crossing's proto edge) or on each side of it in proto edges of their own (`boolean/topology_intersector/coincident_strip.rs`); the strip is then bounded by the existing edges. The same test checks that with the fix the union succeeds with the faces, edges, vertices and regions of the union of the same cubes 5e-6 apart, which upstream makes, and that the fix leaves that union unchanged. That union (both engines, fixture case `wr614_strip_union_d5e-06`) keeps every face use in the infinite region's shell, with no solid region; that is a separate defect.
